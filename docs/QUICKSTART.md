# Quickstart: a first dry run on your own machine

Seven commands take you from nothing to a successful dry run of a small
example configuration, on your own machine, in about fifteen minutes. You
need no cloud account, no login, no identity provider and no key of your
own, and you type nothing but the commands below, exactly as written.
Nothing is applied: a dry run generates everything a real run would
apply, and stops there.

This page covers **macOS and Linux**, on x86_64 and arm64. It does not
cover Windows.

## What you need first

Five tools, at these versions or later. Install them before the first
command; the fifteen minutes do not include them.

Docker means a daemon that answers, not only its command: Docker Desktop,
OrbStack, colima or the engine on a Linux host, started. Linux ships
bash 5; macOS ships 3.2, so on macOS install a newer bash (for example
from Homebrew) and keep it ahead of `/bin/bash` on your `PATH`.

## 1. Install the system

```sh
# step 1 -- box 1 of 3 -- v1
# About a minute on a fresh machine: uv fetches the packages and, if needed, Python 3.13
uv tool install --upgrade --python 3.13 --index-url https://test.pypi.org/simple/ \
  --extra-index-url https://pypi.org/simple/ --index-strategy unsafe-first-match 'cs-image-system[docker]==0.1.13.dev1'
uv tool install --upgrade 'ansible-core>=2.16'
export PATH="$(uv tool dir --bin):$PATH"
cs-image-system --version
```

The last line prints the release you now have, `cs-image-system
0.1.13.dev1`. The first command installs the system with its docker
provider; the second installs ansible-core, which the example's images
are configured with; the third puts both on your `PATH` in this shell
(`uv tool update-shell` makes that permanent). `--python 3.13` is the
Python the system is built and tested on: a newer one may lack a built
package the system needs. Until the system's 1.0
release, its releases are published to TestPyPI, the Python package
index's test instance, and only the system's own packages come from
there: every other package comes from PyPI.

## 2. Write the example and check it

```sh
# step 2 -- box 2 of 3 -- v1
cs-image-system init-config csis-quickstart --from standard-docker
cs-image-system --root-dir csis-quickstart validate
```

The first command writes the example, the `standard-docker` starter, into
a new directory `csis-quickstart` under the one you are in. The last
line prints `Validation successful.`

## 3. The dry run

```sh
# step 3 -- box 3 of 3 -- v1
# One to three minutes the first time: the base image, the packer plugins, the OpenTofu provider
cs-image-system --root-dir csis-quickstart run --all
```

The last line prints `Run <id> completed: identity, storage, base-image,
instance-image, release, retention`.

## What you have now

The dry run generated everything a real run would apply, and applied
none of it:

- `csis-quickstart/generated/` holds the generated configuration for
  each lifecycle: the OpenTofu roots, the Packer templates and the
  scripts a real run would execute;
- `csis-quickstart/meta-state/` holds the run's record.

No container was started and no image was built. Two things stay on your
machine besides `csis-quickstart`: the `almalinux:10` image in your
container daemon's store (the dry run pulls it to pin its digest; `docker
image rm almalinux:10` removes it) and the packer plugins in packer's
plugin directory. The tree also carries a test key (`.age-identity`) for
encrypted values; this example has none, so the key is never read, and
it protects nothing.

Running the three boxes again works: `init-config` finds its own tree and
keeps it as it is, and the dry run runs again.

## The network

Boxes 1 and 3 need the network: box 1 fetches the packages (and Python
3.13, on a machine without it); box 3 pulls the base image and fetches
the packer plugins and the OpenTofu provider. Box 2 works offline. The
slow steps are box 1 on a fresh machine and box 3 the first time; a
second run reuses what the first fetched.
